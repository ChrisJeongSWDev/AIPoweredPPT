+  `subprocess.run` a real file object for `stderr` makes the OS write the child's stderr straight
+  to disk as it is produced — genuinely real-time, not something Python's side buffers — which is
+  what lets `GET /api/log` show a call that is still in flight.

+    onto `result.stderr` (a `subprocess.CompletedProcess` is a plain mutable object, so this
+    assignment is safe) — restoring the pre-existing contract that `result.stderr` holds the
+    process's stderr as a string. This is what the brief's "read the file content back into
+    result.stderr... to avoid breaking existing error handling" asks for; confirmed the one caller
+    that actually reads `result.stderr` on a failure path, `_run_track_b`'s `if result.returncode
+    != 0: raise CliWorkerError(f"...: {result.stderr[-2000:]}")`, still works unchanged against a
+    plain string.
