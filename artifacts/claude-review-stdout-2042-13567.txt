# Phase 1 Renderer — Slide Cloning Architecture

## 0. Verdict from the review stage: FEASIBLE, with four hard conditions

Slide cloning is the right call and it is implementable in `python-pptx` + `lxml`. It is the only one
of codex-critic's three options (F-01) that preserves the template's actual visual grammar, which
lives in slide-level freeform shapes, not in the five thin layouts.

But the naive recipe that circulates on Stack Overflow — `deepcopy` the `spTree` children into a new
slide — **produces a file PowerPoint offers to repair**. It is wrong in four specific ways, and each
one is a condition of this task:

| # | Condition | Why the naive recipe fails |
|---|---|---|
| C-1 | Every relationship id inside the copied XML must be **re-registered on the destination slide part** | `r:embed` / `r:id` / `r:link` point at rels on the *source* part. Deep-copied into a new part they dangle → repair prompt or missing image. §2.2 |
| C-2 | `<p:bg>` and `<p:clrMapOvr>` must be copied too | They are **not** inside `spTree`. An spTree-only copy silently drops a custom background and colour-map override. §2.3 |
| C-3 | Text must be rewritten **run-in-place**, never via `text_frame.text = x` | The setter discards `<a:rPr>`. On this template that means discarding the design — the font (`뷰웍스 B`/`뷰웍스 M`) and the brand red both live in slide-level run properties (Q3 F-03), not in the theme. §4.2 |
| C-4 | Every slot the IR does not bind must be **removed** | Otherwise the exemplar's own demo text ships inside the customer deck. This is *the* signature failure of slide cloning, and a shape-count assertion will not catch it. §4.5 |

## 2. Slide cloning: the recipe

All of this goes in `src/aippt/render/clone.py`. It is the load-bearing module; it gets the most tests.

### 2.1 The skeleton

```python
# src/aippt/render/clone.py
import copy
from pptx.oxml.ns import qn

_R_NS = "http://schemas.openxmlformats.org/officeDocument/2006/relationships"


def clone_slide(prs, src_slide):
    """Append an exact, self-contained copy of ``src_slide`` to ``prs``. Returns the new Slide.

    The copy is *independent*: it survives deletion of ``src_slide`` (§2.5) because every
    relationship it needs has been re-registered on its own slide part (§2.2).
    """
    # 1. Same layout => the layout's decoration (logo, page-number graphic) and its
    #    layout-level DB0032 run styling are inherited exactly as on the source.
    dst = prs.slides.add_slide(src_slide.slide_layout)

    # 2. add_slide() cloned the layout's placeholders into the new slide. We do not want them:
    #    the source slide already carries its own copies of whatever it uses.
    #    Iterate slide.shapes (NOT spTree children -- spTree also holds <p:nvGrpSpPr> and
    #    <p:grpSpPr>, which are structural and must not be removed).
    for shp in list(dst.shapes):
        shp._element.getparent().remove(shp._element)

    _copy_background(src_slide, dst)          # C-2, §2.3
    _copy_clr_map_ovr(src_slide, dst)         # C-2, §2.3

    # 3. Deep-copy every top-level shape, then repair its relationship ids.
    dst_spTree = dst.shapes._spTree
    for shp in src_slide.shapes:
        el = copy.deepcopy(shp._element)
        _remap_rels(src_slide.part, dst.part, el)   # C-1, §2.2  -- BEFORE append
        dst_spTree.append(el)

    return dst
```

Shape-id uniqueness needs no special handling: `<p:cNvPr id>` must be unique *within a slide*, and we
copy one whole slide's shapes into an emptied slide, so the source's ids arrive already consistent.
(This is another reason to clear the destination first rather than append into a live slide.)

### 2.2 C-1 — relationship remapping (the corruption fix)

Every `r:`-namespaced attribute anywhere in the copied subtree is a relationship id scoped to the
source part. Sweep the whole subtree generically rather than enumerating element types — that way you
cover `a:blip/@r:embed` (pictures), `asvg:svgBlip/@r:embed` (the SVG fallback inside a modern picture),
`a:hlinkClick/@r:id` (hyperlinks, including ones on individual text runs), `c:chart/@r:id`,
`p:oleObj/@r:id`, and `p:videoFile/@r:link`, without a whitelist that will inevitably miss one.

```python
def _remap_rels(src_part, dst_part, element):
    """Re-point every r:id / r:embed / r:link in ``element`` at a rel on ``dst_part``."""
    for el in element.iter():
        for attr_name, rid in list(el.attrib.items()):
            if not attr_name.startswith("{%s}" % _R_NS) or not rid:
                continue
            rel = src_part.rels[rid]
            if rel.is_external:
                new_rid = dst_part.relate_to(rel.target_ref, rel.reltype, is_external=True)
            else:
                new_rid = dst_part.relate_to(rel.target_part, rel.reltype)
            el.set(attr_name, new_rid)
```

`Part.relate_to()` is idempotent: the same (target, reltype) pair returns the existing rId rather than
adding a duplicate. So two pictures sharing one image part collapse to one rel, as they should.

**The part-sharing hazard — read this, it is subtle.** `relate_to(rel.target_part, ...)` makes the
clone point at the *same part object* as the source. That is exactly right for parts we only ever
**read** (images, media): sharing them keeps the file small and is safe. It is exactly **wrong** for
parts we intend to **mutate** — a chart part and its embedded workbook. If two IR slides clone the
same chart-bearing exemplar, both clones point at one chart part, and rebranding one recolours the
other.

Phase-1 rule, enforced in the annotation pass, not merely documented:

- **Exemplars may not contain charts or OLE objects.** `analyze_exemplars.py` refuses to emit an
  exemplar whose slide contains `c:chart` or `p:oleObj`, and says why.
- Tables are safe: `a:tbl` is inline XML inside the `graphicFrame`, not a separate part. Mutate freely.
- Objective 3's "force charts to use the company red" therefore applies only to charts **we** create
  with `shapes.add_chart()`, which is Phase 2. Say so in `foundation_research.md`; do not build a
  chart-rebranding path you cannot test.

### 2.3 C-2 — the parts that are not in `spTree`

```python
def _copy_background(src, dst):
    """<p:bg> is a child of <p:cSld> and must be its FIRST child, before <p:spTree>."""
    src_bg = src._element.find(qn("p:cSld")).find(qn("p:bg"))
    if src_bg is None:
        return
    dst_cSld = dst._element.find(qn("p:cSld"))
    existing = dst_cSld.find(qn("p:bg"))
    if existing is not None:
        dst_cSld.remove(existing)
    new_bg = copy.deepcopy(src_bg)
    _remap_rels(src.part, dst.part, new_bg)   # a picture-fill background carries an r:embed
    dst_cSld.insert(0, new_bg)


def _copy_clr_map_ovr(src, dst):
    """<p:clrMapOvr> is a child of <p:sld> and must come AFTER <p:cSld>."""
    src_ovr = src._element.find(qn("p:clrMapOvr"))
    if src_ovr is None:
        return
    dst_sld = dst._element
    existing = dst_sld.find(qn("p:clrMapOvr"))
    if existing is not None:
        dst_sld.remove(existing)
    cSld_pos = list(dst_sld).index(dst_sld.find(qn("p:cSld")))
    dst_sld.insert(cSld_pos + 1, copy.deepcopy(src_ovr))
```

Do not skip the `_remap_rels` call on the background: if any of the 23 slides uses a picture fill, an
un-remapped copy is a dangling rel and a repair prompt.

`<p:transition>` and `<p:timing>` are deliberately **not** copied — they are presentation behaviour,
not design, and the IR does not model them.

Speaker notes are **not** cloned; the IR supplies its own. Mind Q3 F-17: reading `slide.notes_slide`
*creates* the notes slide as a side effect, and `notes_text_frame` can still be `None`. Only touch
`notes_slide` when `ir_slide.notes` is non-empty, and guard the `None`.

### 2.4 What you get for free (and must not re-implement)

Because `add_slide(src.slide_layout)` links the clone to the *same layout part*:

- Layout decoration (`그림 5`, `그래픽 4`, the slide-number graphic) renders identically.
- The layout-level `DB0032` text styling in `slideLayout3.xml` (Q3 F-03) is inherited, not copied.
- The `뷰웍스 B` / `뷰웍스 M` typefaces resolve exactly as they do on the source slide.

This is why cloning beats recipe-extraction. Do not "helpfully" re-apply any of it in code.

### 2.5 Deck assembly and slide ordering

`add_slide` always appends. Exploit that instead of writing a reorder routine:

```
1. prs = Presentation(TEMPLATE)                    # 23 template slides present
2. for each ir_slide, in IR order:
       clone_slide(prs, prs.slides[exemplar.source_slide_index])   # appends at 23, 24, 25...
       fill it (§4)
3. delete the ORIGINAL 23 slides, indices 0..22    # AFTER every clone exists
=> len(prs.slides) == len(ir.slides), in IR order. F-05 satisfied, and no reorder code.
```

Deletion must drop the relationship *and* the `sldIdLst` entry, in that order — the existing
`renderer.py::clear_existing_slides` docstring already has this right:

```python
xml_slides = prs.slides._sldIdLst
for sld in list(xml_slides)[:n_original]:
    prs.part.drop_rel(sld.get(qn("r:id")))
    xml_slides.remove(sld)
```

Dropping the entry without `drop_rel` leaves an orphaned relationship and PowerPoint calls the file
corrupt. Deleting the source slides is safe *only after* every clone has re-registered its own rels
(§2.2) — the image parts then stay reachable through the clones and survive serialisation.

**This ordering is easy to get wrong and the failure is silent until someone opens the file.** Assert
it: clone → delete → save → reopen → every image still resolves (V-2).

## 3. The mapping contract: how a block finds its shape

### 3.1 Two layers

**Layer 1 — annotation (`src/aippt/analyze_exemplars.py`, run once, output committed).**
Walk all 23 slides read-only and emit `reference/exemplar_manifest.json`: for every top-level shape,
its `shape_id` (`cNvPr/@id`), `name`, `z_index` (position in `spTree`), geometry in EMU + inches,
whether it is a placeholder (and its `idx`), its **effective run style read off the slide's own
`<a:rPr>`** (size / typeface / colour / bold — this is where the design actually is), and its current
text. Also emit `reference/exemplar_catalog.md` for humans and for prompt context.

Then **a human assigns `slot_id`s** — semantic names like `title`, `body-main`, `card-1-title`,
`pic-main`, `table-main` — and marks every other shape `role: "decoration"`. This is a one-time pass
over ~8 curated slides, not all 23; it is an hour of work and it is the only place semantics enter the
system. The analyzer must support re-running against the same file and **preserving** hand-assigned
`slot_id`s (merge on `shape_id`, never clobber).

**Layer 2 — resolution (`src/aippt/render/slots.py`, every render).**

```
slot_id  --(exemplar_manifest)-->  shape_id  --(cloned spTree)-->  the shape
```

`shape_id` is the primary key: unique within a slide, stable across renaming and re-ordering, and
broken only if someone deletes and recreates the shape — which is exactly when you *want* a hard
failure. Then verify the fingerprint (`name`, `z_index`, geometry within a 1000-EMU tolerance) and on
mismatch **raise `TemplateDriftError` naming the slot and the delta**. Never fall back, never guess. A
silent substitution here yields a deck that looks fine and is wrong, which is the worst outcome because
nobody notices.

## 4. Content replacement

### 4.1 Order of operations, per slide

```
clone → resolve slots → fill bound slots → remove unbound slots → enforce brand → notes
```

Brand enforcement runs **after** fill so nothing a block writer does can leave an off-brand run behind.
Unbound-slot removal runs **before** brand enforcement so we do not spend work rebranding shapes we are
about to delete.

### 4.2 C-3 — writing text without destroying the design

`text_frame.text = x` and `run.text = x` behave very differently, and the difference is the whole ball
game on this template:

- `tf.text = "x"` → drops every paragraph and every `<a:rPr>`. The 30pt `뷰웍스 B` in `DB0032` becomes
  18pt Calibri black. **Banned.** Grep for it in review.
- `run.text = "x"` → replaces the literal text inside an existing `<a:r>`, leaving its `<a:rPr>`
  untouched. **This is the primitive.**

Single-line slot (title, card title, step title):

```python
def set_text_preserving_style(tf, text: str) -> None:
    p = tf.paragraphs[0]
    if p.runs:
        p.runs[0].text = text                              # keep run[0]'s rPr -- the design
        for extra in p.runs[1:]:
            extra._r.getparent().remove(extra._r)
    else:
        p.add_run().text = text                            # no run to inherit from: last resort
    for extra in tf.paragraphs[1:]:
        extra._p.getparent().remove(extra._p)
```

Multi-paragraph slot (bullets, body prose): harvest a **style prototype** from the exemplar before you
touch anything, then stamp it per line.

```python
def rewrite_paragraphs(tf, lines):        # lines = [(level, RichText), ...]
    """Preserves the exemplar's pPr and rPr per level."""
    txBody = tf._txBody
    protos = {}
    for p in tf.paragraphs:
        protos.setdefault(p.level, copy.deepcopy(p._p))    # one prototype per level seen
    proto0 = protos.get(0) or copy.deepcopy(tf.paragraphs[0]._p)

    for p in list(tf.paragraphs):
        txBody.remove(p._p)

    for level, rich in lines:
        new_p = copy.deepcopy(protos.get(level, proto0))
        _set_runs(new_p, rich, level)      # keep <a:pPr> + <a:endParaRPr>; replace the <a:r>s
        txBody.append(new_p)
```

`_set_runs` must keep `<a:pPr>` (indent, bullet char, spacing) and `<a:endParaRPr>` (the trailing style
hint), delete the existing `<a:r>` / `<a:br>` / `<a:fld>` children, then append one `<a:r>` per IR run
— each carrying a `deepcopy` of the prototype's `<a:rPr>`, with only `b` / `i` / `code` overlaid on
top. If no prototype exists for the requested level, reuse level 0's and set `pPr/@lvl` explicitly.

`code` runs are the one deliberate deviation from inherited styling (111 of them in the corpus):
`run.font.name = "Consolas"` plus `run.font.color.rgb = BRAND_RED`. Everything else — size, typeface,
colour — comes from the prototype. **If you find yourself setting `font.size` anywhere outside
`fit.py`, you have made a mistake.**

### 4.3 Images — swap the blip, keep the frame

The exemplar's picture already has the right position, size, and often a picture style (rounded
corners, a border, a shadow). Deleting it and calling `add_picture()` at the same geometry throws that
style away. Swap the image *part* underneath the existing `<p:pic>` instead:

```python
def replace_picture(slide, pic, image_stream):
    image_part, rId = slide.part.get_or_add_image_part(image_stream)   # -> (ImagePart, rId)
    blip = pic._element.blipFill.find(qn("a:blip"))
    blip.set(qn("r:embed"), rId)
    _fit_srcRect(pic, image_part)
    return pic
```

The trap: the new image is now stretched to the old frame's aspect ratio. PowerPoint's own behaviour
here is **aspect-fill with a centre crop**, expressed as `<a:srcRect>` inside `<a:blipFill>`:

```
frame_ar = pic.width / pic.height
img_ar   = image_part.image.size[0] / image_part.image.size[1]      # needs Pillow
if img_ar > frame_ar:      # image too wide -> crop left/right
    crop = (1 - frame_ar / img_ar) / 2 ;  srcRect(l=crop, r=crop)
else:                      # image too tall -> crop top/bottom
    crop = (1 - img_ar / frame_ar) / 2 ;  srcRect(t=crop, b=crop)
```

`srcRect` units are thousandths of a percent (`50000` = 50%). Reset any inherited `srcRect` first.
Pillow is a **hard** dependency precisely here: without it `image.size` is unavailable and aspect-fill
degrades silently into stretch.

For `kind: "path"` sources: resolve under an approved asset root, reject absolute paths and `..`
traversal, and cap the decoded size (Q3 F-11). All three corpus images are `image/jpeg` data-URIs, not
png — the existing schema comment is right about that.

### 4.4 Tables

The exemplar's `graphicFrame` already holds an `<a:tbl>` with the brand's row banding and column
widths. Prefer **rewriting cells in place** over `shapes.add_table()`:

- Row/column count matches → write cell text with `set_text_preserving_style` on each
  `cell.text_frame`, preserving each cell's `rPr`.
- Row count differs → clone the last body `<a:tr>` (it carries the banding and the cell styles), or
  delete surplus `<a:tr>` elements.
- Column count differs from the exemplar → **hard fail**, and tell the adapter to choose a different
  exemplar. Re-deriving `<a:gridCol>` widths is how you end up with a table that does not fit the slide.

If you must fall back to `shapes.add_table()`, note that it applies Office's default *blue* "Medium
Style 2 – Accent 1" table style. Do not chase that by editing the `tableStyles` part; set the fills
explicitly (§5). Q3 F-12 is also correct that `TablePlaceholder.insert_table()` exists and the current
renderer docstring is wrong about it — this template has no TABLE placeholder so it is moot in
practice, but fix the docstring.

### 4.5 C-4 — the leftover-demo-text problem

**Every slot in the cloned exemplar that no IR block bound must be removed.** Skip this and the
exemplar's own demo content — `"제목을 입력하세요"`, a sample bullet, a stock photo — ships inside the
customer's deck, on brand, in the right font, looking entirely intentional.

```python
for slot in exemplar.slots:
    if slot.slot_id in bound:
        continue
    if slot.required:
        raise IRValidationError(f"slides[{i}]",
                                f"exemplar '{ex.exemplar_id}' requires slot '{slot.slot_id}'")
    shp = resolve(slide, slot)
    if slot.on_unbound == "remove":
        shp._element.getparent().remove(shp._element)
    elif slot.on_unbound == "blank":
        shp.text_frame.clear()     # keeps the box, e.g. a design element that must stay
```

`decorations` are **never** touched — that is the entire point of cloning.

Report the count in `RenderReport.unfilled_slots_removed`, and assert in tests that no rendered slide
still contains any slot's `sample_text` (V-4).

## 5. Brand enforcement (`src/aippt/render/brand.py`)

One module, one constant, one pass. `BRAND_RED = RGBColor(0xDB, 0x00, 0x32)` — see §0 on the `#FF0032`
discrepancy; flag it, default to `DB0032`.

The accent is **not** in the theme (`brand_accent.resolution: "not-found"`, manifest line 53). It is
hardcoded in `slideLayout3.xml` and `slide2.xml`. Therefore `MSO_THEME_COLOR` is **unavailable** and you
must use a literal `RGBColor`. Delete the "take the accent from the theme slot" instruction in the
current `renderer.py::write_rich_text` docstring: it describes a colour source that does not exist in
this file.

`enforce_brand(slide, exemplar, policy)` runs last on every slide and is the single choke point:

- **Tables** — header row: `cell.fill.solid(); cell.fill.fore_color.rgb = BRAND_RED` on row 0, with
  white bold text. Set `table.first_row = True` so the style honours it.
- **Callouts** — the left accent bar and/or the shape line take `BRAND_RED` for `variant: "info"`;
  `warn` and `ok` get their own constants in the same module (do not scatter them).
- **`code` runs** — `font.color.rgb = BRAND_RED` (§4.2).
- **Shapes listed in the exemplar's `brand_shapes: [shape_id, ...]`** — fill or line, per the manifest
  entry. This is how you force a specific design element red without hardcoding geometry in Python.
- **Charts** — not in Phase 1 (§2.2). Say so; do not stub a path you cannot test.

Because it runs after fill, `enforce_brand` is also the right place for a cheap assertion: a run that
should be branded and is not is a bug in the block writer, not something to paper over here.

## 6. IR pivot

### 6.1 `schema.json`

**Slide**, replacing `layout_id`:

```jsonc
"slide": {
  "required": ["id", "exemplar_id", "source_slide_index", "title"],
  "properties": {
    "id":                 { "type": "string", "pattern": "^slide-[0-9]{2,3}$" },  // F-08
    "exemplar_id":        { "type": "string", "minLength": 1 },                   // stable semantic key
    "source_slide_index": { "type": "integer", "minimum": 0, "maximum": 22 },     // as the draft asks
    "title":              { "type": "string", "minLength": 1, "maxLength": 200 },
    "notes":              { "type": "string", "maxLength": 4000 },
    "source_refs":        { "type": "array", "items": { "type": "string" } },     // F-08: provenance survives
    "blocks":             { "type": "array", "maxItems": 12, "items": { "$ref": "#/$defs/block" } }
  }
}
```

**Why both `exemplar_id` and `source_slide_index`, when the draft brief asked only for the index:** a
bare integer index into `prs.slides` is a positional reference with no meaning and no drift detection.
If anyone inserts a slide into the template, every IR ever written silently starts cloning the wrong
design — that is Q3 F-10 restated. Carrying both costs nothing and lets `models.py` assert
`manifest[exemplar_id].source_slide_index == slide.source_slide_index`, hard-failing on drift. The index
is still there and still authoritative for the clone call, exactly as specified. **If you disagree,
argue it in the result — do not silently drop one.**

**Deck**: add `"template_sha256"` (required) — pin the template the IR was authored against and refuse
to render against a different one (F-10). Remove the "the renderer turns `deck.title` into a title
slide" language: **one IR slide → one PPTX slide, always** (F-05). The title slide is an explicit IR
slide with `exemplar_id: "deck-title"`. Code-variant expansion and overflow splits happen in a
normalisation pass that emits new IR with final ids — never inside the renderer.

**Block**: every block gets an `"id"` (unique within the slide, F-08) and a `"slot_id"` (which slot of
the exemplar it targets, F-06). Ordered-position mapping is gone.

**Also fix while you are in here** (Q3 findings, all cheap):

- `steps.items.maxItems`: 6 → **10**. The corpus contains a ten-step process
  (`Vieworks_MatroxSDK_Example_UserManual.html:350-359`), so the schema currently rejects a construct it
  claims to have derived from the corpus (F-07). Let the budget decide whether to split, not the cap.
- `image.source.value`: add `maxLength` and a media-type constraint (F-11).
- SVG policy: one explicit sentence — supported, pre-converted, or an accepted loss with a named
  exception list. Pick one and write it down (F-07).

### 6.2 `models.py`

Q3 F-09 is right and it is a real hole: `Deck.from_dict()` currently bypasses JSON-Schema validation
entirely, so a `Deck` can be constructed that the "normative contract" would reject. Fix the shape of
the boundary, not just the symptoms:

- **One public entrypoint**: `Deck.parse(data, *, manifest)` → runs `jsonschema` against `schema.json`
  **first**, then the cross-field checks. Rename the unchecked path to `Deck._from_dict_unchecked()` and
  keep it private.
- Cross-field checks it must own (JSON Schema structurally cannot express these): slide `id` unique
  deck-wide; block `id` unique per slide; `exemplar_id` exists in the exemplar manifest;
  `source_slide_index` matches that exemplar; every `slot_id` exists on that exemplar and accepts that
  block type (`supports_blocks`); every `required` slot is bound; every table row has exactly
  `len(columns)` cells; `deck.template_sha256` matches the manifest's.
- Add `jsonschema` to `requirements.txt` / `pyproject.toml`, alongside `pillow` and `pytest`.

### 6.3 `html_adapter.py`

`choose_layout()` → `choose_exemplar()`, matching each card's shape against `exemplar.roles` /
`supports_blocks` instead of the seven layout roles that do not exist (F-01). It must also **assign a
`slot_id` per block** — that is now the adapter's job. An unmatched card is a hard failure carrying the
card index; never a silent fallback to a `bullets` exemplar that may not exist.

### 6.4 `fit.py`

Budgets now come from the **slot's own box plus its effective font size read off the exemplar's `rPr`**,
not from a layout placeholder. That is a strict improvement and it is what finally makes F-04 tractable:
we are measuring the box the text actually lands in. Subtract the text-frame margins
(`tf.margin_left/right/top/bottom`, which python-pptx exposes directly), account for `pPr` indent and
`space_before` / `space_after`, and keep the render→PNG check as the final authority. `fit.py` is the
**only** module allowed to change a font size.
