## The issue (WARNING)
`var multi` (the alignment set) is cleared on every **interactive** path the diff added — background click, plain click, Escape, insert, paste — but **not** on the two paths that tear down and rebuild every `.el` node:

- `restore()` (undo/redo) removes all nodes and rebuilds via `makeEl` (editor.js:519, 528), sets `selected = null`, but leaves `multi` pointing at the now-detached old nodes.
- `loadIR()` does the same (editor.js:1991-1992) without clearing `multi`.

Reachable failure: Shift+Click to build a 2+ element alignment set, then press Ctrl+Z (or load/paste a deck). `multi` now holds detached corpses. `selectionSet()` still counts them, so the Align panel shows a stale count, and clicking Left/Right/Center runs `alignSelection()` → `bboxOf(read(ghost))` on frozen dataset coordinates and `commit()`s a translate on the **live** element toward those invisible deleted positions — moving a live element to align with ghosts (wrong geometry the user didn't request). Recoverable via undo, but it's a normal-workflow sequence producing incorrect output.

Suggested fix: call `clearMulti()` in `restore()` and `loadIR()` (and defensively filter `selectionSet()` to `el.isConnected`). Minor related nit: deleting the `selected` element doesn't prune it from `multi`, though the plain-click-clears-multi rule makes that hard to hit.

Everything else in the diff is sound and internally consistent; this single state-hygiene omission is the only defect, hence WARNING rather than BLOCK.
