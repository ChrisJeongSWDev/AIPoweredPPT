# Phase 1 Renderer — Slide Cloning Architecture

## 0. Verdict from the review stage: FEASIBLE, with four hard conditions

Slide cloning is the right call and it is implementable in `python-pptx` + `lxml`. It is the only one
of codex-critic's three options (F-01) that preserves the template's actual visual grammar, which
lives in slide-level freeform shapes, not in the five thin layouts.

But the naive recipe that circulates on Stack Overflow — `deepcopy` the `spTree` children into a new
slide — **produces a file PowerPoint offers to repair**. It is wrong in four specific ways, and each
one is a condition of this task:

| # | Condition | Why the naive recipe fails |
|---|---|---|
| C-1 | Every relationship id inside the copied XML must be **re-registered on the destination slide part** | `r:embed` / `r:id` / `r:link` point at rels on the *source* part. Deep-copied into a new part they dangle → repair prompt or missing image. §2.2 |
| C-2 | `<p:bg>` and `<p:clrMapOvr>` must be copied too | They are **not** inside `spTree`. An spTree-only copy silently drops a custom background and colour-map override. §2.3 |
| C-3 | Text must be rewritten **run-in-place**, never via `text_frame.text = x` | The setter discards `<a:rPr>`. On this template that means discarding the design — the font (`뷰웍스 B`/`뷰웍스 M`) and the brand red both live in slide-level run properties (Q3 F-03), not in the theme. §4.2 |
| C-4 | Every slot the IR does not bind must be **removed** | Otherwise the exemplar's own demo text ships inside the customer deck. This is *the* signature failure of slide cloning, and a shape-count assertion will not catch it. §4.5 |

And one thing the draft brief got wrong, which you must resolve before writing a line of code:

> **Brand-red conflict RESOLVED BY USER.** The draft brief originally said the company red is `RGB(255, 0, 50)` = `#FF0032`. While the template internally uses `#DB0032` (219, 0, 50), the USER HAS EXPLICITLY OVERRIDDEN THIS.
> **You MUST default to `#FF0032`**, define it in exactly one place (`render/brand.py::BRAND_RED`), and use it to forcefully override the legacy template colors in the renderer. Do NOT use `#DB0032`.

### 1.1 The finding that kills the obvious mapping contract

The draft brief asks: *"How will the renderer identify which shape gets which text — by shape name,
type, or z-order?"*

**Shape name is not usable as a key on this template, and here is the proof.** In
`reference/layout_manifest.json`, layout `1_사용자 지정 레이아웃` has three *different* placeholders — idx
10, idx 11, idx 12, at three different `top` values and three different font sizes (28pt / 36pt /
16pt) — and **all three are named `텍스트 개체 틀 8`** (manifest lines 161, 195, 225). Layout 0 has two
placeholders both named `텍스트 개체 틀 2`. These are PowerPoint's auto-generated Korean names. They are
neither semantic nor unique.

So `shape.name` **cannot** be the primary key. Neither can placeholder `idx` (the content is in
non-placeholder freeform shapes). Neither can raw z-order alone (stable, but meaningless to a human
and silently wrong the moment anyone re-orders a shape in the deck).

The contract in §3 solves this with a **curated slot manifest keyed on `cNvPr/@id`, fingerprinted by
name + z-order + geometry**. Read §3 before you write any renderer code.
